Methodology

How the Impact Score is built

The one-line summary on the dashboard is accurate but compressed. This section unpacks each piece — what it counts, why it's shaped the way it is, and a small worked example for each, so a number on a card is never something you have to just trust.

The starting premise. GitHub activity cannot show total employee impact — it can't see roadmap judgment, cross-team negotiation, incident response outside a PR, or mentorship that never produced a commit. What it can show, reliably, is three things: how structurally consequential someone's shipped code is, how much they've helped teammates ship, and whether a team routes a given area of the codebase to them. That's what's scored here — nothing more is claimed.

The three components

Every merged PR in the trailing 90 days feeds into three independently-computed signals. Each is turned into a percentile rank (0–100) across all engineers before being weighted and summed into the single Impact Score shown on each card.

45% weight
Shipped Scope
How structurally consequential is this person's typical merged PR — measured by how many other engineers also depend on the files it touches.
 35% weight
Leverage on Others
How much has this person helped teammates ship, via substantive code review — not rubber-stamp approvals.
 20% weight
Domain Stewardship
Which subsystems does this person's activity concentrate in strongly enough to be one of the top two people active there.

What's filtered out before any of this runs

ExcludedWhy
Bot & automated-tool activity Any account typed as a GitHub Bot, plus a login-pattern backstop for tools that don't carry that type (CodeRabbit, Greptile, Dependabot, Renovate, and PostHog's own internal review bot, stamphog) — these can review or open PRs at a volume that would drown out human signal if left in.
Mechanical PRs Dependency-bump titles and lockfile-only diffs are excluded from all three scored components — they don't reflect engineering judgment, and would inflate Shipped Scope in particular, since lockfiles are touched by almost everyone.
Rubber-stamp reviews A review only counts toward Leverage or Stewardship if its state is an actual verdict (approve or request-changes) and it carries a non-trivial comment — a bare "LGTM" doesn't count as help given.

What's deliberately not scored

Merged PR count, number of distinct collaborators, and median time-to-merge are shown on every card for context, but none of them feed the score. An earlier version of this dashboard did let PR volume leak into the scoring indirectly (see each component page for the specific bug and fix) — the current formulas are built to survive the question "does the person who merges the most just win?" with a genuine no.

Everything is deterministic

The ranking itself is plain Python arithmetic over the fetched GitHub data — no model makes a judgment call about who's more "impactful." The only place AI-generated text appears is the short "why" sentence on each top-5 card, written after the ranking is already fixed, and only to summarize evidence that's independently linked and checkable.
