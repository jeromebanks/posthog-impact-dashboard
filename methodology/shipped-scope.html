Shipped Scope

How structurally consequential is a person's typical merged PR — not how many PRs they merge, and not how many lines or files each one touches.

The intuition

If you change a file that only you ever touch, the blast radius of getting it wrong is small — you find out, you fix it, nobody else was depending on it. If you change a file that a dozen other engineers also regularly touch, you're operating in shared, load-bearing territory: more people are depending on that code being right, and more people would be affected if it weren't. Shipped Scope tries to measure the second thing — how many other engineers' work intersects with yours — using nothing but "who touched which files, when," which is the one signal GitHub data can give cleanly.

The formula

for every file in the 90-day window:
    file_weight(file, this_PR) = sqrt(
        count of OTHER engineers (not this PR's author)
        who also touched `file` somewhere in the window
    )

PR_reach = mean(file_weight) across all files the PR touches

Engineer_reach = mean(PR_reach) across all of the engineer's
                 merged, non-mechanical PRs

Shipped Scope = percentile_rank(Engineer_reach) across all engineers

Why sqrt()

Without damping, a file touched by 40 other people would count for literally 40x a file touched by 1 other person — a single very "hot" shared file (a core schema, a widely-imported utility) would dominate the whole score for anyone unlucky or lucky enough to touch it. Square-rooting compresses that: going from 1 co-toucher to 4 only doubles the weight, not quadruples it. It still rewards touching shared territory — it just stops one hotspot file from swamping everything else.

Why average across files, not sum

Summing the per-file weights within a PR would mean a 20-file PR automatically scores higher than a 1-file PR, structural consequence held equal — the PR would win on file count alone, which is exactly the kind of size-proxy this metric exists to avoid. Averaging measures the PR's typical file, regardless of how many files it happens to touch.

Why average across PRs, not sum

This is the more important of the two averages. Summing an engineer's per-PR contributions across all their merged PRs would mean whoever simply merges the most PRs wins, even with the per-file averaging fix in place — someone with 400 PRs of modest reach can out-accumulate someone with 20 PRs of very high reach. Averaging measures the typical consequence of this person's work, which is what "impact per PR" is actually supposed to mean, and is what makes it possible for someone with very few but very consequential PRs to rank highly (see the worked example below).

This is a proxy for structural reach, not business impact. Touching code many engineers depend on is a real, defensible signal — but GitHub data cannot tell you whether that code shipped a feature customers loved or fixed a bug nobody noticed. Shipped Scope answers "how load-bearing is this person's typical change," not "how much revenue did it generate."

Worked example

Two toy engineers, three files in the window, to make the arithmetic concrete.

FileTouched byOther engineerssqrt(weight)
billing/invoice.pyalice, ben, cho, dan31.73
billing/currency.pyalice, ben11.00
billing/README.mdalice only00.00

Alice ships one PR that touches all three files above:

PR reachmean(1.73, 1.00, 0.00) = 0.91
Engineer reach (1 PR)0.91

Ben ships five small, low-traffic PRs elsewhere in the codebase that nobody else happens to touch that quarter:

PR reach (each of 5 PRs)0.00 (no co-touching engineers)
Engineer reach (5 PRs)0.00

Alice ends up ranked above Ben on this component despite merging one-fifth as many PRs — because her single PR sat in genuinely shared, consequential territory, and averaging (rather than summing) means Ben's extra volume in low-traffic code doesn't out-accumulate that. This is the exact case an earlier, buggy version of this metric got backwards: it summed rather than averaged, so Ben's volume alone would have won.

What's excluded going in

  • Mechanical PRs (lockfile-only diffs, dependency bumps) don't contribute a file-touch record to the shared map at all — otherwise a lockfile, which nearly every PR in a monorepo touches at merge time in some workflows, would look like the most "consequential" file in the repo for reasons that have nothing to do with engineering judgment.
  • Bot-authored PRs are excluded the same way, for the same reason.
