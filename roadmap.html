Roadmap

What's next

The dashboard scores individuals over one fixed 90-day window because that was the right scope for a time-boxed build. Two things came up while building it that a real engineering leader would actually want next — both listed first, both genuinely bigger than a 90-minute add-on. The rest is a shorter list of smaller, deferred ideas.

The two big ones

Next

Subsystem / module drill-down

Right now Domain Stewardship is a single number folded into each engineer's score — it doesn't say which subsystems, or who else is active there. A dedicated per-scope view (billing, flags, ai-research, plugin-server, …) would show, for one subsystem at a time:

  • Everyone active there this window, ranked — not just the top-2 who earn scoring credit
  • Subsystem-level context: PR volume, review latency, bot-vs-human PR mix
  • A bus-factor flag — subsystems where stewardship credit concentrates in a single person are a single-point-of-failure risk, and that's arguably the single most actionable thing a subsystem view could surface. It's a more useful question for a leader than "who's #1 overall": "which parts of the codebase have exactly one person who really knows them?"

Mechanically cheap to add — the scope is already parsed and stored per PR (see the stewardship methodology) — the work is mainly a new aggregation pass and a second page template, not a new data pipeline.

Next

Trends over time

The current dashboard is one static snapshot of a single 90-day window. That can't distinguish "consistently strong contributor" from "caught a temporary spike right before the window closed" — and it gives no sense of whether the whole org's pace this quarter was normal or unusual. A time-series view would add:

  • Rolling per-engineer Impact Score over several trailing windows (e.g. weekly, each still a 90-day lookback) — a trajectory, not a point estimate
  • Org-wide series: merged PR volume, review latency, bot-vs-human PR mix, week over week — the context a single snapshot can't provide
  • Ramp-up tracking for newly active engineers — e.g. time to first substantive review given, as an onboarding-health signal distinct from the impact score itself

The scoring logic (scripts/score.py) is already parameterized by a date window, so this is largely a re-run-at-multiple-windows problem rather than a redesign — the real cost is the data footprint (multiple 90-day fetches instead of one) and the GraphQL rate-limit budget that comes with it, which is why it didn't fit the original time box.

Smaller deferred ideas

Later

Team rollups

If GitHub Teams or a CODEOWNERS-style mapping were incorporated, scores could roll up to team level, not just individual — useful for a leader who thinks in terms of teams first and people second.

Later

Cross-repo scope

Currently scoped to posthog/posthog only. PostHog engineers also ship to posthog-js and other repos in the org — a fuller picture would pull from all of them, deduplicated by author across repos.

Later

Tenure-aware normalization

A two-month-old hire and a three-year veteran are being percentile-ranked against the same pool right now. Normalizing by tenure (or at least segmenting new joiners into their own comparison group for their first quarter) would make the score fairer without diluting the "who's the best right now" read for everyone else.

Later

Reliability signal

PR titles containing "revert," or issues explicitly closed by a PR (GraphQL's closingIssuesReferences, a field not currently fetched), could support a light reliability/impact-on-users signal — shipped work that measurably fixed something reported, versus work that had to be walked back. Deliberately not folded into the score without more validation that it wouldn't just penalize people who ship more (and therefore revert more, in absolute terms).

Later

Real avatars, scheduled regeneration

Two smaller polish items: pull each engineer's actual GitHub avatar instead of a bare login string, and move from a one-off manual snapshot to a scheduled GitHub Actions job that regenerates data/scores.json on a cadence (nightly or weekly) so the dashboard stays current without a person re-running the pipeline by hand.

Deliberately never

An LLM will not be added to the ranking path. This is a design decision, not a gap to fill later — see the methodology overview for why ranking stays fully deterministic. AI-assisted text generation (the "why" card copy) stays scoped to summarizing evidence after a ranking is already fixed by plain arithmetic, and that boundary is intentional going forward too.
